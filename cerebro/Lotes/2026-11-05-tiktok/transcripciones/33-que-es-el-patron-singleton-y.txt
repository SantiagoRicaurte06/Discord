## Transcripción
[00:00] Si tu app abre una conexión nueva a la base de datos cada vez que alguien la pide, con 100 usuarios tendrás 100 conexiones abiertas. El servidor se satura y para evitarlo existe el patrón singleton. El problema aparece con objetos que deberían ser únicos, como la configuración, el logger o el pull de conexiones. Si cada parte del código crea su propia copia con new, desperdicias, recursos y cada copia puede tener datos distintos. La idea del singleton es sencilla. La clase garantiza que solo exista una instancia y ofrece un único punto de acceso global para obtenerla. Todos le piden el objeto y todos reciben el mismo. En TypeScript se ve así. El constructor es privado, así que nadie puede usar new desde afuera. Una propiedad estática guarda la instancia y el método GetInstance la crea solo la primera vez. En ejecución, la primera llamada no encuentra ninguna instancia y la crea. A partir de ahí, cada llamada a GetInstance devuelve exactamente el mismo objeto, por eso la comparación da verdadero.

[01:07] Pero ojo con esto, porque un singleton es estado global disfrazado. Las dependencias quedan ocultas y las pruebas se contaminan entre sí. Además, en lenguajes con hilos, dos hilos pueden crear dos instancias a la vez si no sincronizas la creación. Por eso, úsalo cuando de verdad necesitas una única instancia compartida, como un logger o la configuración. Y si tu framework tiene inyección de dependencias, deja que el contenedor cree esa instancia única y te la entregue. El singleton no consiste en tener una variable global, consiste en controlar quién crea el objeto y cuantas veces. Cuéntame en los comentarios dónde lo has usado.
